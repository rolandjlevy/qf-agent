## What Phase 2 is

Two things, sequenced. The first is load-bearing; the second is
cheap follow-on once the first is done.

### Phase 2a — Trader identity persistence

The single biggest gap in Phase 1 is that every quote is generated
from scratch with no memory of the trader. Business name, contact
details, and hourly rate are all `[BUSINESS NAME]`-style placeholders
in the output, requiring manual find-and-replace before the trader
can send. Every quote also uses placeholder prices because there's
no notion of what _this trader_ actually charges.

Phase 2a fixes both by persisting a **trader profile** and using it
in every subsequent quote. Concretely:

- The trader identity data (name, contact details, hourly rate,
  standard T&Cs)
- The trader's own historical quotes (uploaded or imported)
- The trader's own material prices, derived from those historical
  quotes

Once persisted, the agent uses this in every quote:

- Placeholders get filled in automatically
- `lookup_price` prefers the trader's own historical prices over
  `data/sample-prices.json`, falling back to samples only when the
  trader has no history for that item
- Sub-LLM `draft_section` calls receive the trader's T&Cs and voice
  as context so the tone is consistent with what they'd actually
  write

### Phase 2b — Lightweight web UI

Once identity persistence works, wrap the existing agent in a
minimal web UI. Not a full Next.js reimplementation of QuoteFetch —
just enough that a trader can use the tool without a terminal:

- One page for the trader profile (fill in identity, upload past
  quotes)
- One page for creating a new quote (job description input, agent
  runs, quote appears)
- One page for viewing past quotes generated by the tool

The existing `agent.js` and `tools/` must be reused unchanged from
this UI. This is the reuse boundary the Phase 1 architecture was
designed for. Do not fork the agent loop.

## What Phase 2 is NOT

Explicit, because the temptation is real:

- **Not the price scraper.** Phase 3 in the roadmap remains Phase 3.
  Real prices from Screwfix/Toolstation/etc. are deferred. Trader's
  own historical prices (from Phase 2a) are the price story for now.
- **Not auth.** No login, no user accounts, no password. Phase 2 is
  single-tenant — one trader per install. Phase 4 in the roadmap
  handles multi-tenant auth. If you find yourself building `bcrypt`
  or JWT anywhere, stop.
- **Not a rewrite.** `agent.js`, the tool interfaces, and
  `prompts/system.js` should be untouched or minimally touched. The
  handoff doc explicitly names the reuse boundary — respect it.
- **Not new tools.** No new entries in `TOOL_DEFINITIONS`. Phase 2
  is about giving the existing tools better data (trader context,
  trader prices), not adding capability.
- **Not tests, yet.** The handoff doc acknowledges the lack of
  automated tests. I want tests added, but as a separate follow-on
  after Phase 2a and 2b work. Don't slow Phase 2 down writing them.
- **Not a database refactor.** Use the simplest persistence that
  works. See the "storage" section below.

## Load-bearing constraints from Phase 1

These must not regress:

- The never-do rules in `prompts/system.js` still apply to every
  quote. Trader-supplied prices don't relax the "no invented prices"
  rule — if the trader hasn't priced item X and the sample DB
  doesn't have it, `lookup_price` still returns `found: false` and
  the agent adapts.
- The `executeTool` choke point in `tools/index.js` still validates
  and error-wraps every tool call. Any new context passed to tools
  goes through the same discipline.
- `agent.js` remains domain-free. Trader context is passed _to_
  tools (via their input or via a context object), not baked into
  `agent.js`'s loop.
- The `sample-prices.json` fallback still works when there's no
  trader history. No breakage of Phase 1's CLI behaviour when the
  trader profile is empty.
- Multiple tool calls per turn still work. Any refactor of
  `agent.js` that touches the loop must preserve this.
- The devcontainer `remoteEnv=""` handling for
  `ANTHROPIC_API_KEY`/`CLAUDE_MODEL` in `qf.js` stays intact. If you
  move this logic, name the new location.

## Storage — opinionated choice

Use **SQLite via `better-sqlite3`**. Single file, no server, ESM-
compatible, and appropriate for a single-tenant Phase 2. Schema
lives in a single migration file; no migration framework yet.

Suggested tables (adjust as needed):

- `trader_profile` — one row, holding name, contact details, hourly
  rate, standard T&Cs, voice sample text
- `trader_prices` — many rows: material name, canonical name,
  aliases, unit, unit price, source (`historical_quote` |
  `manual_entry`), source reference, updated_at
- `historical_quotes` — many rows: original file path, imported_at,
  extracted text, extraction status, notes
- `generated_quotes` — many rows: job description input, output
  path, generated_at, tool call log (JSON blob)

Store the DB file at `data/qf.db`. Add it to `.gitignore`.

If you want to argue for a different storage choice (JSON files, a
`data/`-directory-per-record, something else), do so in the plan
before writing code — but justify it against SQLite's specific
advantages for this shape of data.

## Trader price lookup — modifying `tools/lookup-price.js`

The existing tool takes a material name and does word-overlap fuzzy
matching against `data/sample-prices.json`. Modify it (do NOT
replace it) so:

1. First, query `trader_prices` for a match using the same fuzzy-
   match logic (score threshold 40, same as sample DB).
2. If found, return with `source: 'trader_history'` and `verified:
true` (the trader has actually paid this).
3. If not found, fall back to `sample-prices.json` with the existing
   behaviour (`verified: false`).
4. If neither has it, return `found: false` — unchanged.

The `verified` flag from the trader's own prices should flow through
to the system prompt exactly as it does today. Real prices no longer
carry the "please verify" auto-note; sample prices still do.

## Quote-history import — new tool or new sub-command

The trader needs to import their past quotes so the system learns
their prices and voice. Two shapes are reasonable:

- **A new CLI sub-command** (`node qf.js import <path>`) that reads
  a PDF/DOCX/MD quote, extracts materials and prices, and populates
  `trader_prices`.
- **A new agent tool** (`import_quote`) that the trader-onboarding
  flow calls.

Pick one and justify it in the plan. My weak preference is the sub-
command — it's a batch operation, not something the agent should
reason about turn-by-turn. But if there's a reason the tool shape
fits better, say so.

For extraction, use an LLM sub-call (same pattern as
`identify_materials.js`). Extract `{ material_name, quantity, unit,
unit_price, currency }` per line. Store in `trader_prices` with
source `historical_quote`.

## Trader profile — how it reaches the agent

The trader profile is context, not conversation. It should be
available to:

- The main agent loop's `system` prompt — appended to
  `SYSTEM_PROMPT` from `prompts/system.js` so Claude knows the
  trader's name, rate, voice, T&Cs
- Sub-LLM calls in `identify_materials.js` and `draft_section.js`
  — passed via the shared context
- `save_quote.js` — used to fill in the header placeholders
  (`[BUSINESS NAME]`, `[CONTACT DETAILS]`, etc.) automatically

Load the profile once at the start of a run, in `qf.js` (or the web
handler equivalent), and pass it to `runAgent()` as an additional
context argument. Do NOT read it from disk inside individual tools.

## Web UI — Phase 2b specifics

Use **Next.js 14 (App Router)** with the existing `agent.js` and
tools imported directly. No new HTTP layer between them.

Pages:

- `/profile` — form for trader identity, upload past quotes
- `/quote/new` — job description input, live progress display as
  agent runs
- `/quote/[id]` — view a generated quote
- `/quotes` — list of past quotes

State is server-side via SQLite. No Redux, no client state library.
This is a small internal tool for now.

The progress display should reuse `agent.js`'s existing `onStep`
callback pattern. Stream tool-call events to the client via
server-sent events or Next.js streaming. The exact mechanism is
your call — reuse a pattern from the Next.js docs rather than
inventing one.

## What good looks like

- Trader fills in profile once. Uploads 3-5 past quotes. Total
  onboarding time under 10 minutes.
- Trader types a new job description. Quote generates in under 60
  seconds. All placeholders filled. Prices reflect trader's own
  history where possible. Output is send-ready with zero find-and-
  replace.
- Existing CLI (`node qf.js "..."`) still works, including with an
  empty profile (falls back to Phase 1 behaviour).
- `agent.js` diff is minimal. Tool interfaces unchanged. Sample
  price DB still works as a fallback.
